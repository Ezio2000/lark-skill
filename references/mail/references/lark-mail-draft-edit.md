# mail +draft-edit


Edit an existing mail draft. The command reads the current raw EML, applies a minimal patch, then writes the updated draft back.

Use direct parameters for simple metadata edits:
- `--set-subject`
- `--set-to`
- `--set-cc`
- `--set-bcc`

**Shortcut for full body replacement:** `--body <text>` / `--body-file <path>` (mutually exclusive, choose one) automatically expand to the `set_body` op. If you only want to do a full body replacement and do not need to preserve the quoted region, use these two flags; no patch-file is needed. To preserve the quoted region or do a more fine-grained combination of ops, still use `--patch-file`. The two entry points are mutually exclusive with `set_body` / `set_reply_body` inside `--patch-file`.

**CRITICAL - Before editing mail content you MUST first use the Read tool to read [lark-mail-html.md](lark-mail-html.md), which contains the mail writing guidelines**

<a id="正文编辑快捷-flag-与-typed-op-的选择"></a>
## Body editing: choosing between shortcut flags and typed ops

When replacing the entire body and you do not need to preserve the quoted region, you can directly use `--body` / `--body-file`. When you need to preserve the quoted region, modify the quoted region, or combine advanced body edits, pass a typed body op via `--patch-file`; there are two ops to choose from:

| Situation | op | Behavior |
|------|-----|------|
| Normal draft (no quoted region) | `set_body` | Replace the user-authored content |
| Reply/forward draft, editing the user-authored part | `set_reply_body` | Replace the user-authored part, automatically re-concatenating the quoted region. The value passed in contains only the new user-authored content, **do not include the quoted region** |
| Reply/forward draft, editing the quoted region content | `set_body` | Pass in HTML containing the complete quoted region for replacement |
| User explicitly wants to remove the quoted region | `set_body` | Simply do not include the quoted region |

**How to determine:** Run `--inspect`; if it returns `has_quoted_content: true`, the draft contains a quoted region (generated by `+reply` or `+forward`).

**Key differences:**
- The value of `set_reply_body` = **pure user-authored content** (excluding the quoted region); the quoted region is automatically re-concatenated
- The value of `set_body` = may or may not include the quoted region

**System-managed elements are automatically preserved (applies to both ops):** The signature block (`lark-mail-signature`) and the large attachment card (`large-file-area-*`) are not part of the user-authored content; they are draft-level elements managed by ops such as `insert_signature` / `add_attachment`. Both `set_body` and `set_reply_body` automatically preserve them (regular attachment MIME parts are likewise unaffected by body edits). If the value explicitly includes the corresponding element, the user's explicit specification is respected and no automatic injection occurs. To delete a signature/attachment, use the corresponding dedicated op (`remove_signature` / `remove_attachment`).

<a id="正文编辑plainhtml-耦合草稿"></a>
### Body editing: plain+HTML coupled draft

When a draft contains both `text/plain` and `text/html` parts, they form a coupled pair. Both `set_body` and `set_reply_body` update the HTML body and automatically regenerate the plain text summary. In this case, be sure to pass HTML as the input, because the original main body is `text/html`.

<a id="安全约束"></a>
## Safety constraints

This command updates a real draft. Before invoking, confirm with the user:
1. Draft ID
2. Final recipient scope (To/Cc/Bcc)
3. Final subject and body
4. Whether attachments, inline images, or other advanced edits are needed

<a id="命令"></a>
## Command

```bash
# Edit draft metadata (subject, recipients)
lark-cli mail +draft-edit --draft-id <draft-id> --set-subject '更新后的主题' --set-to alice@example.com,bob@example.com

# Quick full body replacement
lark-cli mail +draft-edit --draft-id <draft-id> --body '<p>更新后的正文</p>'

# Advanced body editing (e.g. preserving the reply/forward quoted region)
lark-cli mail +draft-edit --draft-id <draft-id> --patch-file ./patch.json

# View draft (read-only) — returns a projection containing has_quoted_content, attachments_summary, and inline_summary
lark-cli mail +draft-edit --draft-id <draft-id> --inspect

# Print patch template
lark-cli mail +draft-edit --print-patch-template

# Dry Run (only print the request, do not execute)
lark-cli mail +draft-edit --draft-id <draft-id> --set-subject '测试' --dry-run
```

<a id="通用参数"></a>
## Common parameters

| Parameter | Required | Description |
|------|------|------|
| `--mailbox <email>` | No | Email address, specifies the mailbox the draft belongs to (defaults back to `--from`, then back to `me`). Takes precedence over `--from`. Available mailboxes can be queried via `accessible_mailboxes` |
| `--draft-id <id>` | Yes | Target draft ID. Can be omitted only when `--print-patch-template` is used alone |
| `--set-subject <text>` | No | Replace the subject with this value |
| `--set-to <emails>` | No | Replace the entire To recipient list with the addresses provided here |
| `--set-cc <emails>` | No | Replace the entire Cc list with the addresses provided here |
| `--set-bcc <emails>` | No | Replace the entire Bcc list with the addresses provided here |
| `--body <text>` | No | Replace the entire body (automatically expands to the `set_body` op). Mutually exclusive with `--body-file`; mutually exclusive with the `set_body` / `set_reply_body` ops inside `--patch-file` |
| `--body-file <path>` | No | Read body HTML from a file (relative path, restricted to the cwd subtree). Mutually exclusive with `--body`. File size limit 32 MB |
| `--set-priority <level>` | No | Set mail priority: `high`, `normal`, `low`. Setting to `normal` clears any existing priority |
| `--set-event-summary <text>` | No | Set the calendar title. Requires setting `--set-event-start` and `--set-event-end` at the same time |
| `--set-event-start <time>` | Conditionally required | Set the calendar start time (ISO 8601) |
| `--set-event-end <time>` | Conditionally required | Set the calendar end time (ISO 8601) |
| `--set-event-location <text>` | No | Set the calendar location |
| `--remove-event` | No | Remove the calendar invitation from the draft. Mutually exclusive with `--set-event-*` |
| `--patch-file <path>` | No | Entry point for typed body ops (`set_body` / `set_reply_body`), incremental recipient edits, mail header edits, attachment changes, and inline image changes. Relative path. Run `--print-patch-template` first to view the JSON structure |
| `--print-patch-template` | No | Print the JSON template for `--patch-file` and the supported operations. Recommended to run this command before generating a patch file. Does not read or write the draft |
| `--inspect` | No | View the draft without modifying it. Returns a draft projection containing `has_quoted_content` (whether there is a quoted region), `attachments_summary` (regular attachments, including `part_id`/`cid`/`filename`), `large_attachments_summary` (large attachments, including `token`/`filename`/`size_bytes`), and `inline_summary` |
| `--request-receipt` | No | Append a `Disposition-Notification-To: <草稿的 From 地址>` header to the draft to request a read receipt (RFC 3798). Essentially injects a `set_header` op into the patch; an existing DNT value will be overwritten. Can be combined with other `--set-*` / `--patch-file` edits, or used alone |
| `--format <mode>` | No | Output format: `json` (default) / `pretty` / `table` / `ndjson` / `csv` |
| `--dry-run` | No | Only print the request, do not execute |

<a id="--patch-file-格式"></a>
## `--patch-file` format

Recommended workflow:

1. Run `--inspect` to view the draft's current state (whether there is a quoted region, attachments, etc.)
2. Run `--print-patch-template` to view the JSON structure
3. Generate a patch file conforming to that structure
4. Run `--patch-file`

`--patch-file` accepts a project-specific typed patch JSON format, not RFC 6902 JSON Patch.

Top-level structure:

```json
{
  "ops": [
    { "op": "set_subject", "value": "更新后的主题" }
  ],
  "options": {
    "rewrite_entire_draft": false,
    "allow_protected_header_edits": false
  }
}
```

`options` fields:

- `rewrite_entire_draft`: default `false`. Set to `true` only when the edit requires synthesizing or restructuring body parts (for example, adding a missing main body part). Normal subject, recipient, body, attachment, and inline image edits keep `false`.
- `allow_protected_header_edits`: default `false`. Set to `true` only when the user explicitly wants to edit protected mail headers and understands the possible conversation archiving or delivery risks. For normal use keep `false`.

<a id="主题与正文"></a>
### Subject and body

`set_subject`

```json
{ "op": "set_subject", "value": "更新后的主题" }
```

`set_body` — replace user-authored content

```json
{ "op": "set_body", "value": "<p>全新的正文内容</p>" }
```

> **Note:** `set_body` does not automatically preserve the quoted region (if the user wants to preserve the quoted region they can include it in the value themselves, or switch to `set_reply_body`). System-managed elements (signature, large attachment card, regular attachments) are automatically preserved.

`set_reply_body` — replace user-authored content, automatically preserving the quoted region

```json
{ "op": "set_reply_body", "value": "<p>新的回复内容</p>" }
```

> **The value should contain only the user-authored content; do not include the quoted region.** The quoted region is automatically extracted from the original draft and re-concatenated after the value. The signature, large attachment card, and regular attachments are also automatically preserved.
>
> If the user wants to modify content in the quoted region (for example, correcting an error in the quote), they must use `set_body` to pass in the complete HTML (including the modified quoted region).
>
> If the draft has no quoted region, `set_reply_body` behaves the same as `set_body`.

<a id="收件人"></a>
### Recipients

`set_recipients`

```json
{ "op": "set_recipients", "field": "to", "addresses": [{ "address": "alice@example.com", "name": "Alice" }] }
```

`add_recipient`

```json
{ "op": "add_recipient", "field": "cc", "address": "alice@example.com", "name": "Alice" }
```

`remove_recipient`

```json
{ "op": "remove_recipient", "field": "cc", "address": "alice@example.com" }
```

<a id="邮件头"></a>
### Mail headers

`set_header`

```json
{ "op": "set_header", "name": "X-Custom", "value": "abc" }
```

`remove_header`

```json
{ "op": "remove_header", "name": "X-Custom" }
```

<a id="附件与内嵌图片"></a>
### Attachments and inline images

**How to obtain the locating fields:** Different attachment types have different locating fields, all obtained from `--inspect`:

- **Regular attachments**: `part_id` or `cid` (from `projection.attachments_summary`)
- **Large attachments**: `token` (from `projection.large_attachments_summary`)
- **Inline images**: `part_id` or `cid` (from `projection.inline_summary`)

These values come from the draft's MIME structure and header parsing, and are **different** from the public API's attachment IDs.

```bash
lark-cli mail +draft-edit --draft-id <draft_id> --inspect
```

`add_attachment` — unified entry point, does not distinguish between regular/large. When cumulative attachments cause the total EML size to exceed 25 MB, the excess is automatically handled as large attachments, with a per-file limit of 3 GB.

```json
{ "op": "add_attachment", "path": "./report.pdf" }
```

`remove_attachment` — unified entry point. `target` accepts `part_id` / `cid` (regular attachments) or `token` (large attachments). Priority: `part_id` > `cid` > `token`.

```json
{ "op": "remove_attachment", "target": { "part_id": "1.3" } }     // Regular attachment, by part_id
{ "op": "remove_attachment", "target": { "cid": "logo" } }         // Regular attachment, by CID
{ "op": "remove_attachment", "target": { "token": "12101..." } }  // Large attachment, by file token
```

`add_inline`

```json
{ "op": "add_inline", "path": "./logo.png", "cid": "logo" }
```

> **Recommended approach:** Directly use `<img src="./logo.png" />` (relative path) in the HTML of `set_body`/`set_reply_body`; the system automatically creates the MIME inline part, generates a CID, and replaces it with a `cid:` reference. Only relative paths are supported (such as `./logo.png`); absolute paths are not supported. When a `<img>` tag is deleted or replaced, the corresponding MIME part is automatically cleaned up. See [Inserting inline images in the body](#在正文中插入内嵌图片).
>
> `add_inline` is used only when precise control over CID naming is needed. When using it, you still need to add a `<img src="cid:...">` reference in the HTML body.

`replace_inline`

```json
{ "op": "replace_inline", "target": { "part_id": "1.2" }, "path": "./new-logo.png", "filename": "new-logo.png", "content_type": "image/png" }
{ "op": "replace_inline", "target": { "cid": "logo" }, "path": "./new-logo.png" }
```

In `replace_inline`, `filename` and `content_type` are optional. When omitted, the original inline part's filename and content type are preserved. `target` accepts `part_id` or `cid`.

`remove_inline`

```json
{ "op": "remove_inline", "target": { "part_id": "1.2" } }
{ "op": "remove_inline", "target": { "cid": "logo" } }
```

`insert_signature`

```json
{ "op": "insert_signature", "signature_id": "<签名ID>" }
```

Insert a signature at the end of the body (before the quoted block). If a signature already exists, remove it first and then insert. Run `mail +signature` to get available signature IDs. Template variables in the signature are automatically replaced, and inline images are automatically downloaded and embedded.

`remove_signature`

```json
{ "op": "remove_signature" }
```

Remove the existing signature from the draft (including the blank line spacing before the signature). If the signature contains inline images and the body no longer references those images, the corresponding MIME parts are also removed.

Notes:

- `ops` are executed in order
- `target` accepts `part_id` or `cid`; priority: `part_id` > `cid`
- **All file paths (`--body-file`, `--patch-file`, and `path` in ops) must be relative paths**
- **For quick full body replacement use `--body` / `--body-file`; for advanced body editing use `--patch-file`**
- **`set_body` replaces user-authored content** — does not preserve the old quoted region (if the user wants to preserve it, include it in the value, or switch to `set_reply_body`); automatically preserves the signature, large attachment card, and regular attachments
- **`set_reply_body` replaces user-authored content** — automatically preserves the quoted region, signature, large attachment card, and regular attachments; the value should contain only the user-authored part, do not include the quoted region/signature/attachment card; if the user wants to modify the quoted region content, use `set_body` and include the modified quoted region in the value
- **Deleting a signature / attachment** cannot be achieved by clearing `set_body` — you must use the corresponding dedicated op: `remove_signature`, `remove_attachment` (located by `part_id` / `cid` / `token`)
- The `has_quoted_content` field returned by `--inspect` can be used to determine whether the draft contains a quoted region
- The `has_signature` / `signature_id` fields returned by `--inspect` can be used to determine whether the draft contains a signature

<a id="返回值"></a>
## Return value

On success:

```json
{
  "ok": true,
  "data": {
    "draft_id": "草稿ID",
    "warning": "This edit flow has no optimistic locking. If the same draft is changed concurrently, the last writer wins."
  }
}
```

Optional fields:

- `reference`: Draft open link. **Only appears when the current edit chain actually returns it.**

If the update result includes `reference`, the draft open link should be returned to the user together with `draft_id`; if there is currently no link, handle it silently.

<a id="典型场景"></a>
## Typical scenarios

<a id="获取草稿--编辑--发送"></a>
### Get draft → edit → send

```bash
# 1. View the draft's current state
lark-cli mail +draft-edit --draft-id <draft_id> --inspect

# 2. Edit the draft (metadata and quick body replacement)
lark-cli mail +draft-edit --draft-id <draft_id> --set-subject '最终版本' --body '<p>更新后的内容</p>'

# 3. Send the draft
lark-cli mail user_mailbox.drafts send --params '{"user_mailbox_id":"me","draft_id":"<draft_id>"}'
```

<a id="编辑回复转发草稿的正文"></a>
### Editing the body of a reply/forward draft

The body of a reply or forward draft contains a quoted region (the original mail quote block). When editing, you need to use `set_reply_body` to preserve the quoted region.

```bash
# 1. View the draft to confirm whether there is a quoted region
lark-cli mail +draft-edit --draft-id <draft_id> --inspect
# Returns:
#   has_quoted_content: true  ← indicates there is a quoted region, should use set_reply_body
#   body_html_summary: "<div>original reply content</div>..."

# 2. Use set_reply_body to edit the body (the value should contain only the user-authored content, excluding the quoted region)
cat > ./patch.json << 'EOF'
{ "ops": [{ "op": "set_reply_body", "value": "<p>修改后的回复内容</p>" }] }
EOF
lark-cli mail +draft-edit --draft-id <draft_id> --patch-file ./patch.json
```

**Note:** If `set_body` is used by mistake, the quoted region will be overwritten and lost. If the user explicitly wants to remove the quoted region or modify the quoted region content, then `set_body` should be used.

<a id="从草稿中移除附件"></a>
### Removing attachments from a draft

`remove_attachment` handles both regular and large attachments uniformly; choose the corresponding locating field based on the `--inspect` output.

```bash
# 1. View the draft to obtain attachment locating information
lark-cli mail +draft-edit --draft-id <draft_id> --inspect
# Returns:
#   projection.attachments_summary (regular attachments):
#     [{"part_id":"1.3","filename":"report.pdf","content_type":"application/pdf"}]
#   projection.large_attachments_summary (large attachments):
#     [{"token":"12101...","filename":"video.mov","size_bytes":314572800}]

# 2. Write the patch file. Use part_id (or cid) for regular attachments, and token for large attachments
cat > ./patch.json << 'EOF'
{
  "ops": [
    { "op": "remove_attachment", "target": { "part_id": "1.3" } },
    { "op": "remove_attachment", "target": { "token": "12101..." } }
  ]
}
EOF

# 3. Apply the patch
lark-cli mail +draft-edit --draft-id <draft_id> --patch-file ./patch.json
```

<a id="在正文中插入内嵌图片"></a>
### Inserting inline images in the body

Simply use a relative path directly in the HTML of `set_body`/`set_reply_body` (such as `./logo.png`; absolute paths are not supported). The system automatically creates the MIME inline part and replaces it with a `cid:` reference.

```bash
# 1. View the draft to obtain the current HTML body
lark-cli mail +draft-edit --draft-id <draft_id> --inspect

# 2. Write the patch — use the relative path directly (note: use set_reply_body for reply drafts, set_body for normal drafts)
cat > ./patch.json << 'EOF'
{
  "ops": [
    { "op": "set_body", "value": "<div>内容<img src=\"./logo.png\" /><img src=\"./photo.jpg\" /></div>" }
  ]
}
EOF

# 3. Apply the patch
lark-cli mail +draft-edit --draft-id <draft_id> --patch-file ./patch.json
```

Adding, deleting, and modifying inline images is automatically linked through the HTML body:
- **Add**: Write `<img src="./image.png" />` in the HTML; the MIME part is automatically created
- **Delete**: Remove the `<img>` tag from the HTML; the corresponding MIME part is automatically cleaned up
- **Replace**: Change `src` to a new relative path; the old MIME part is automatically removed and the new part is automatically created

> **Advanced usage:** When precise control over CID naming is needed, you can still use `add_inline` to manually add a MIME part and reference it in the HTML with `<img src="cid:your-cid">`.

<a id="使用-patch-file-进行高级编辑"></a>
### Advanced editing with patch-file

```bash
# 1. View the patch template
lark-cli mail +draft-edit --print-patch-template

# 2. Write the patch file (for example, add a Cc and remove an attachment)
cat > ./patch.json << 'EOF'
{
  "ops": [
    { "op": "add_recipient", "field": "cc", "address": "carol@example.com", "name": "Carol" },
    { "op": "remove_attachment", "target": { "part_id": "1.3" } }
  ],
  "options": {}
}
EOF

# 3. Apply the patch
lark-cli mail +draft-edit --draft-id <draft_id> --patch-file ./patch.json
```
