# mail +send-receipt


Respond to a received read receipt request. **This command is only used when the other party's email requested a read receipt (`READ_RECEIPT_REQUEST` label, system ID `-607`)**, to send a short reply to the original sender to inform them "read".

This module corresponds to shortcut: `lark-cli mail +send-receipt`.

<a id="critical--工作流与安全规则"></a>
## CRITICAL — Workflow and Security Rules

1. **Strict trigger condition**: Only when fetching mail (`+message` / `+messages` / `+thread`) and seeing `READ_RECEIPT_REQUEST` in `label_ids` should you ask the user whether to send a receipt. For ordinary emails, **never** call this command.
2. Only execute when the user requests or has authorized sending a read receipt; merely reading an email does not authorize a receipt. When the target and action are already clear, do not ask again.
3. **`--yes` is not omitted**: This command is marked as `high-risk-write`, and the framework requires `--yes` before executing (no `--confirm-send` flag). Only attach it after user confirmation.
4. **Fail-safe**: If the original email does not have the `READ_RECEIPT_REQUEST` label, the command will refuse to execute and report an error — this is a defense; do not bypass it by other means.

<a id="命令"></a>
## Command

```bash
# Standard usage: send a receipt for the specified message-id
lark-cli mail +send-receipt --message-id <message-id> --yes

# Specify mailbox (shared mailbox scenario)
lark-cli mail +send-receipt --mailbox shared@example.com --message-id <message-id> --yes

# Dry Run (do not actually send)
lark-cli mail +send-receipt --message-id <message-id> --dry-run
```

<a id="参数"></a>
## Parameters

| Parameter | Required | Default | Description |
|------|------|------|------|
| `--message-id <id>` | Yes | — | Message ID of the original email that requested a read receipt |
| `--mailbox <email>` | No | `me` | Mailbox to which the receipt email belongs |
| `--from <email>` | No | Mailbox primary address | Receipt From header |
| `--yes` | Yes | — | Confirm high-risk write operation. Only attach after the user explicitly agrees to send a receipt |
| `--dry-run` | No | — | Only print the request, do not execute |

> **There is no `--body` parameter**: The receipt body is **automatically generated by the command** (see "Behavior Details" below), aligning with industry convention (Outlook / Thunderbird / Lark client, etc. all do not support customizing the receipt body per email). If you really need a free-form reply, use `mail +reply` instead — that is inherently the "free reply" command and should not be mixed with "read receipt".

<a id="行为细节"></a>
## Behavior Details

- **Subject**: Automatically select the prefix according to the original email subject language (`detectSubjectLang`) — <code>Read receipt:&lt;original email subject&gt;</code> (zh) or <code>Read receipt:&nbsp;&lt;original email subject&gt;</code> (en). The backend `GetRealSubject` regex strips these two types of prefixes for conversation aggregation; zh is built in; en needs to be added to TCC `MailPrefixConfig.SubjectPrefixListForAdvancedSearch` as `Read receipt:`.
- **Body** (automatically generated, plain text + HTML dual versions via `multipart/alternative`):
    - Switch between `zh` and `en` according to the original email subject language (`detectSubjectLang`); the label set is centrally maintained via `receiptMetaLabels`
    - Structured 4 lines (plain text version, zh):
      ```text
      The email you sent has been read. Details are as follows:
      > Subject: <original email subject>
      > Recipient: <receipt sender address>
      > Sent time: <original email sent time>
      > Read time: <current time>
      ```
    - en version: `Your message has been read. Details:` + <code>Subject:&nbsp;</code> / <code>To:&nbsp;</code> / <code>Sent:&nbsp;</code> / <code>Read:&nbsp;</code>
    - The HTML version has the same information content, wrapped in a light gray quote-block
- **Conversation threading**: Automatically set `In-Reply-To` (the original email's SMTP Message-ID) and `References` (the original email's references + the original email's SMTP Message-ID), ensuring it aggregates into the original email's reply chain in the sender's mailbox.
- **Send path**: Uses the existing drafts raw path (`drafts.create` + `drafts.send`), sharing infrastructure with `+send` / `+reply`. The backend will automatically mark this as a receipt email and clear the "request receipt" status in the original email conversation.
- **Immediate send**: This command does not support saving drafts — a receipt email is semantically "immediately inform the other party it has been read", so saving a draft is meaningless.

<a id="返回值"></a>
## Return Value

```json
{
  "ok": true,
  "data": {
    "message_id":             "回执邮件的 message ID",
    "thread_id":              "挂到原会话的 thread ID",
    "receipt_for_message_id": "原邮件的 message ID"
  }
}
```

`message_id` can be used for subsequent `send_status` queries of delivery status.

<a id="典型场景"></a>
## Typical Scenarios

<a id="场景-1用户在拉信时看到--607-标签"></a>
### Scenario 1: User sees the `-607` label while fetching mail

```bash
# 1. Fetch mail
lark-cli mail +message --message-id msg-1 --format json | jq '.data.label_ids'
# Output ["UNREAD", "READ_RECEIPT_REQUEST"] → the original email requested a read receipt

# 2. Prompt the user:
#    "This email from alice@example.com requests a read receipt. Subject: 《Weekly Report》.
#     Would you like to reply to let the other party know you have read it?"

# 3. Send the receipt after user confirmation
lark-cli mail +send-receipt --message-id msg-1 --yes
```

<a id="场景-2批量拉信中发现多封请求回执"></a>
### Scenario 2: Multiple receipt requests found during batch mail fetching

```bash
# 1. Filter out emails with the -607 label
lark-cli mail +triage --folder INBOX --format json \
  | jq '.data.messages[] | select(.label_ids | index("READ_RECEIPT_REQUEST")) | {message_id, subject, from}'

# 2. Ask the user separately for each email → send only after user confirmation
```

<a id="场景-3公共邮箱的回执"></a>
### Scenario 3: Receipt for a shared mailbox

```bash
# For receipt requests received by a shared mailbox, specify with --mailbox
lark-cli mail +send-receipt --mailbox support@example.com --message-id <id> --yes
```

<a id="不要这样做"></a>
## Do Not Do This

- ❌ **Automatic receipt** (sending without user confirmation) — violates privacy rules
- ❌ Call `+send-receipt` on ordinary emails (the command will refuse, but the agent should not attempt it either)
- ❌ Manually compose a "read receipt" reply using `+send` / `+reply` — it will lack the `X-Lark-Read-Receipt-Mail` header, the backend will not tag it with `-608`, and the recipient will not see the system-style receipt
- ❌ Send multiple in one call (this command is designed for a single response)
